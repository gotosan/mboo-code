# Code Agent 工具与权限设计

## 文档状态

- 状态：草案，待确认。
- 更新时间：2026-07-20。
- 适用范围：当前 `mboo-code` 本地 Code Agent 后端。
- 本文依据 Claude Code、Codex、OpenCode 的公开设计以及当前项目实际代码整理，不以项目内既有工具规划文档作为设计依据。

## 目标

为 Agent 增加在指定工作区内理解代码、修改文件和执行项目命令的能力，同时建立清晰的工具边界、权限决策和审计机制。

第一阶段需要解决：

1. Agent 能查找、搜索和读取工作区内的代码。
2. Agent 能安全地局部修改或创建文本文件。
3. Agent 能在用户授权后执行构建、测试和格式化命令。
4. 工作区、权限和审批状态由服务端注入，模型不能伪造。
5. 工具调用过程能够通过 SSE 展示，并写入 JSONL 审计日志。

第一阶段暂不解决：

- 删除和移动文件。
- 长时间后台命令和进程托管。
- 远程工作区和多用户隔离。
- 完整的操作系统级 Shell 沙箱。
- 服务重启后自动恢复等待审批的工具调用。

## 参考产品

### Claude Code

Claude Code 将代码文件操作拆分为五个主要工具：

- `Glob`：按文件名模式查找文件。
- `Grep`：搜索文件内容。
- `Read`：读取文件内容。
- `Edit`：精确字符串替换。
- `Write`：创建文件或整文件覆盖。

命令执行使用 `Bash`，Windows 环境可以提供独立的 `PowerShell`。长时间后台监听另有 `Monitor`，不与普通命令执行混合。

权限特点：

- 工作区内的读取、搜索默认不询问。
- 文件修改默认需要审批。
- Shell 默认需要审批，但部分内置只读命令可以直接执行。
- 权限规则支持 `allow`、`ask`、`deny`。
- 权限规则和操作系统沙箱是两层独立机制。
- `Edit` 权限可以覆盖多个文件修改工具，模型工具数量不等于权限数量。

参考：

- [Claude Code Tools reference](https://code.claude.com/docs/en/tools-reference)
- [Claude Code Permissions](https://code.claude.com/docs/en/permissions)

### OpenCode

OpenCode 提供以下文件工具：

- `glob`
- `grep`
- `read`
- `edit`
- `write`
- `patch`

命令执行使用 `bash`。其中 `edit`、`write` 和 `patch` 虽然是三个模型工具，但统一由 `edit` 权限控制。

权限特点：

- 支持 `allow`、`ask`、`deny`。
- 可以按工具输入使用通配符规则。
- 工作区外访问使用独立的 `external_directory` 权限。
- `.env` 默认禁止读取，`.env.example` 默认允许。
- 审批支持单次允许、当前会话持续允许和拒绝。

参考：

- [OpenCode Tools](https://opencode.ai/docs/tools/)
- [OpenCode Permissions](https://opencode.ai/docs/permissions/)

### Codex

Codex 本地代码操作的核心工具面较小：

- 使用统一命令执行工具进行文件发现、读取和项目命令执行。
- 使用 `apply_patch` 修改文件。

该设计依赖较强的操作系统沙箱。沙箱负责限制文件系统和网络边界，审批策略负责决定何时允许跨越边界。

常见沙箱模式：

- `read-only`
- `workspace-write`
- `danger-full-access`

常见审批策略：

- `untrusted`
- `on-request`
- `never`

参考：

- [Codex Agent approvals and security](https://learn.chatgpt.com/docs/agent-approvals-security)

## 设计结论

当前项目不宜直接采用 Codex 的“Shell + apply_patch”最小工具面，原因是项目尚未具备能够覆盖 Shell 及其子进程的操作系统级沙箱。普通读取和搜索如果全部经过 Shell，会扩大命令审批和路径隔离的复杂度。

建议采用以下折中方案：

- 模型侧提供六个职责单一的工具。
- 权限侧合并为四个能力组。
- 第一版使用精确字符串替换，不提供 `apply_patch`。
- Shell 独立授权，不承担普通代码读取和搜索。
- 文件工具使用应用层工作区边界；Shell 后续再增加操作系统级沙箱。

## 模型工具设计

### 工具总览

| 工具 | 权限组 | 是否有副作用 | 第一阶段默认策略 |
| --- | --- | --- | --- |
| `glob_files` | `read` | 否 | 工作区内允许 |
| `search_text` | `read` | 否 | 工作区内允许 |
| `read_file` | `read` | 否 | 工作区内允许 |
| `edit_file` | `edit` | 是 | 询问 |
| `write_file` | `edit` | 是 | 询问 |
| `run_command` | `command` | 可能有 | 询问 |

### `glob_files`

用途：按 glob 模式查找工作区内的文件。

建议参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `pattern` | `String` | 是 | 例如 `src/**/*.java`、`*.gradle` |
| `path` | `String` | 否 | 相对工作区的搜索起点，默认为 `.` |
| `maxResults` | `Integer` | 否 | 最大结果数量，服务端限制上限 |

结果至少包含：

- 工作区相对路径。
- 文件类型。
- 是否截断。

边界：

- 只返回路径，不返回文件内容。
- 默认排除 `.git` 和常见大型构建目录。
- 默认遵循项目忽略规则。
- 结果达到上限时明确返回 `truncated=true`，模型需要缩小范围。

### `search_text`

用途：在工作区文件内容中搜索文本或正则表达式。

建议参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `query` | `String` | 是 | 搜索文本或正则表达式 |
| `path` | `String` | 否 | 搜索起点，默认为 `.` |
| `glob` | `String` | 否 | 文件过滤，例如 `**/*.java` |
| `regex` | `Boolean` | 否 | 是否按正则处理 |
| `caseSensitive` | `Boolean` | 否 | 是否区分大小写 |
| `maxResults` | `Integer` | 否 | 最大匹配数量 |

结果至少包含：

- 文件相对路径。
- 行号。
- 匹配片段。
- 是否截断。

实现优先使用 `rg`，不可用时再使用 Java 实现兜底。

### `read_file`

用途：读取工作区内文本文件的指定行范围。

建议参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `path` | `String` | 是 | 工作区相对路径 |
| `offset` | `Integer` | 否 | 起始行，默认从第一行开始 |
| `limit` | `Integer` | 否 | 最大读取行数 |

结果至少包含：

- 文件相对路径。
- 带行号的内容。
- 实际起止行。
- 文件总行数。
- 文件内容哈希。
- 编码和换行符信息。
- 是否截断。

边界：

- 只读取文件，不读取目录。
- 第一阶段只支持能够可靠解码的文本文件。
- 二进制文件和超大文件返回明确错误。
- 文件结果大小由服务端限制，不能由模型放大到无限值。

### `edit_file`

用途：通过精确字符串替换修改已有文本文件，是普通代码修改的首选工具。

建议参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `path` | `String` | 是 | 工作区相对路径 |
| `oldText` | `String` | 是 | 必须精确匹配的旧文本 |
| `newText` | `String` | 是 | 替换后的文本 |
| `replaceAll` | `Boolean` | 否 | 是否替换全部匹配，默认 `false` |
| `expectedHash` | `String` | 否 | Agent 最近读取到的文件哈希 |

执行规则：

1. 文件必须存在且为文本文件。
2. Agent 原则上应先通过 `read_file` 读取文件。
3. `oldText` 必须与当前文件内容精确匹配。
4. `replaceAll=false` 时，`oldText` 必须只出现一次。
5. 提供 `expectedHash` 时，哈希不一致应返回内容已变化错误。
6. 写入采用同目录临时文件和原子替换，尽量保留原编码、换行符和文件属性。

结果至少包含：

- 文件相对路径。
- 修改前后哈希。
- 替换次数。
- 修改字节数或行数。
- 截断后的 diff 摘要。

### `write_file`

用途：创建新文件，或者在明确需要时整文件覆盖已有文件。

建议参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `path` | `String` | 是 | 工作区相对路径 |
| `content` | `String` | 是 | 完整文件内容 |
| `expectedHash` | `String` | 否 | 覆盖已有文件时使用 |
| `createParents` | `Boolean` | 否 | 是否创建缺失的父目录 |

执行规则：

- 新文件不要求预先读取。
- 覆盖已有文件前必须已经读取，并提交对应哈希。
- 不提供追加、局部合并或隐式删除能力。
- 局部修改必须使用 `edit_file`。
- 写入采用临时文件和原子替换。

### `run_command`

用途：执行构建、测试、格式化、Git 查询等项目命令。

建议参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `command` | `String` | 是 | 完整命令字符串 |
| `cwd` | `String` | 否 | 工作区相对工作目录，默认为工作区根目录 |
| `timeoutMs` | `Long` | 否 | 超时时间，受服务端上限限制 |

结果至少包含：

- `stdout`。
- `stderr`。
- 退出码。
- 执行时长。
- 是否超时。
- 输出是否截断。

第一阶段边界：

- 不支持交互式命令。
- 不支持向运行中进程继续写入标准输入。
- 不支持脱离会话的后台进程。
- `cwd` 必须位于工作区内。
- 输出和执行时间必须限制。
- 命令授权不能替代操作系统沙箱；已授权命令仍可能访问工作区外文件、网络和子进程。

## 后续工具

以下工具根据实际效果再考虑：

- `apply_patch`：用于 unified diff 或批量补丁，归属于 `edit` 权限。
- `monitor_command`：运行并持续监听后台进程，归属于 `command` 权限。
- `delete_file`：删除文件，需要独立的高风险确认。
- `move_file`：移动或重命名文件，需要独立的高风险确认。
- `read_many_files`：减少大量小文件读取时的工具调用次数。
- `lsp_query`：定义跳转、引用查找、诊断等代码智能能力。

## 权限模型

### 权限动作

每次工具调用最终解析为以下动作之一：

| 动作 | 说明 |
| --- | --- |
| `ALLOW` | 直接执行 |
| `ASK` | 暂停并请求用户审批 |
| `DENY` | 拒绝执行 |

### 权限组

| 权限组 | 包含工具 | 说明 |
| --- | --- | --- |
| `read` | `glob_files`、`search_text`、`read_file` | 工作区内只读访问 |
| `edit` | `edit_file`、`write_file`、未来的 `apply_patch` | 所有文件修改 |
| `command` | `run_command`、未来的 `monitor_command` | Shell 和子进程执行 |
| `external_directory` | 所有工具 | 访问工作区外路径时额外触发 |

模型工具需要按职责拆分，权限则按风险合并，避免用户分别配置多个等价的写权限。

### 权限模式

| 模式 | `read` | `edit` | `command` | `external_directory` |
| --- | --- | --- | --- | --- |
| `READ_ONLY` | `ALLOW` | `DENY` | `DENY` | `DENY` |
| `MANUAL` | `ALLOW` | `ASK` | `ASK` | `DENY` |
| `WORKSPACE_WRITE` | `ALLOW` | `ALLOW` | `ASK` | `DENY` |
| `FULL_ACCESS` | `ALLOW` | `ALLOW` | `ALLOW` | 待定 |

建议默认模式为 `MANUAL`。

第一阶段建议不开放 `FULL_ACCESS`。当前项目没有操作系统级 Shell 沙箱，放开命令权限等同于允许当前 Java 进程权限范围内的任意操作。

### 决策顺序

建议采用以下优先级：

1. 系统硬拒绝规则。
2. 显式 `DENY` 规则。
3. 显式 `ASK` 规则。
4. 显式 `ALLOW` 规则。
5. 当前权限模式的默认值。

系统硬拒绝至少包括：

- 路径逃逸和工作区外访问。
- 通过符号链接或 Windows Junction 逃逸。
- 修改 `.git` 内部文件。
- 访问非法路径、设备路径和 Windows ADS。
- 超过服务端工具限制。

### 工具可见性

- 整个工具被 `DENY` 时，不应通过 `ToolProvider` 暴露给模型。
- 工具只对部分路径或命令被限制时，工具仍可暴露，执行阶段再根据实际参数决定。
- 模型不能通过工具参数传入权限模式、工作区根目录或审批状态。

### 审批选项

建议前端提供：

| 选项 | 说明 |
| --- | --- |
| `ONCE` | 只批准当前工具调用 |
| `SESSION` | 在当前 session 内批准同类调用 |
| `REJECT` | 拒绝当前工具调用 |

建议授权范围：

- `edit + SESSION`：允许当前 session 在当前工作区内继续修改文件。
- `command + SESSION`：第一阶段只记忆完全相同的规范化命令，不自动放宽为 `git *`、`npm *` 等前缀。
- 工作区外路径和系统硬拒绝不提供普通审批绕过能力。

第一阶段不将审批结果持久化到应用重启之后，避免旧授权自动影响后续会话。

## 工作区安全边界

### 工作区来源

当前项目已经把 `workspacePath` 保存到 session，这是后续工具隔离的基础。

请求仍允许直接提交任意绝对路径。仅依赖前端目录选择器不能形成可信边界，因为 API 调用者可以绕过目录选择接口。

建议方案：

1. 后端目录选择接口返回短期 `workspaceToken` 或已注册的 `workspaceId`。
2. 创建 session 时提交 token 或 ID，而不是重新提交任意绝对路径。
3. 后端解析并保存实际工作区路径。
4. 后续 turn 只根据 session 中的工作区执行，不接受请求覆盖。

如果产品明确定位为仅监听本机回环地址的单用户桌面应用，也可以继续接受路径，但仍需要校验目录存在和真实路径。

### 路径解析

所有文件工具统一经过工作区路径组件，不在各工具中重复实现。

建议校验流程：

1. 工具只接收工作区相对路径。
2. 将路径解析到 session 工作区。
3. 拒绝绝对路径、非法路径和明显的 `..` 越界。
4. 已存在路径使用真实路径校验。
5. 新文件使用最近一个已存在父目录的真实路径校验。
6. 使用 `Path.startsWith()` 判断路径关系，不使用字符串前缀。
7. 校验符号链接、Windows Junction 和不同盘符。
8. 所有校验完成后再执行读取或修改。

当前 `toAbsolutePath().normalize()` 只能完成语法归一化，不能阻止符号链接或 Junction 逃逸。

### 敏感文件

建议默认拒绝读取：

- `.env`
- `.env.*`
- `*.pem`
- `*.key`
- 常见 SSH 私钥文件
- 明确的凭据文件

建议允许 `.env.example` 等不包含真实凭据的示例文件。

具体敏感文件规则仍待确认。

## 权限与沙箱

权限和沙箱分别解决不同问题：

- 权限决定“是否允许尝试执行”。
- 沙箱决定“即使执行，技术上最多能访问什么”。

文件工具可以通过 Java 应用层路径校验限制在工作区内，但 `run_command` 会启动任意子进程。仅设置 `cwd` 不能阻止命令：

- 使用绝对路径访问工作区外文件。
- 修改用户目录或系统目录。
- 访问网络。
- 启动其他子进程。
- 读取 Java 进程继承的环境变量。

在操作系统沙箱完成前，`run_command` 只能被视为“用户明确授权后的本机进程执行”，不能宣称为工作区隔离执行。

第一阶段可选策略：

1. 本机单用户模式下允许命令审批执行，并在 UI 明确显示风险。
2. 在 OS 沙箱完成前完全关闭 `run_command`。

该选择待确认。

## 审批执行流程

### 目标流程

```text
模型发起工具调用
  -> ToolProvider 已确认工具整体可见
  -> PermissionService 根据实际参数计算 ALLOW / ASK / DENY
  -> ALLOW：执行工具
  -> DENY：返回结构化拒绝结果
  -> ASK：写入并推送审批事件
      -> 前端展示工具、参数摘要、风险和授权范围
      -> 用户提交 ONCE / SESSION / REJECT
      -> 后端继续执行或拒绝工具
  -> 写入工具执行结果
  -> LangChain4j 继续模型工具循环
```

### 当前框架约束

当前 LangChain4j AI Service 会自动执行工具循环，依赖版本中没有现成的人机审批暂停和恢复接口。

如果第一阶段实现实时审批，需要新增：

- `ToolApprovalService`，保存待审批调用和等待句柄。
- SSE 审批事件。
- 独立审批接口。
- 审批超时和客户端取消处理。
- 工具执行线程等待与恢复机制。
- session 级临时授权缓存。

第一阶段可以在 SSE 连接存活期间挂起当前工具调用。服务重启后，未完成调用先按未知结果处理，不自动重试有副作用的工具。

另一种简化方案是在每个 turn 开始前预先选择权限模式，执行期间不产生实时审批。该方案实现简单，但交互体验弱于 Claude Code，后续加入实时审批时可能需要调整工具执行流程。

实时审批还是 turn 预授权仍待确认。

## 事件与审计

### 建议事件

除现有工具开始和结束事件外，实时审批方案需要增加：

- `APPROVAL_REQUIRED`
- `APPROVAL_RESOLVED`

审批事件至少记录：

- `toolCallId`
- `toolName`
- 参数摘要
- 权限组
- 风险说明
- 可选授权范围
- 审批结果
- 审批时间

### 参数审计

当前项目直接记录模型提交的原始工具参数。文件工具接入后会出现以下问题：

- `write_file` 参数包含整份文件内容。
- `edit_file` 参数包含完整的旧文本和新文本。
- 代码、密钥或其他敏感信息可能进入 JSONL。
- 大参数会使事件日志快速膨胀。

建议每个工具提供独立的审计序列化逻辑。JSONL 默认只记录：

- 文件相对路径。
- 操作类型。
- 修改前后哈希。
- 文件大小。
- 修改行数或替换次数。
- 截断后的 diff。
- 命令、工作目录、退出码和截断输出。

模型工具循环可以使用完整结果，JSONL 和前端只使用经过裁剪的审计结果。

是否保存完整 diff 或完整文件内容仍待确认。

该上下文由服务端构造，不能由模型参数覆盖。
