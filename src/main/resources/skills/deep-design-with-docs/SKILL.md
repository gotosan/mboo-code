# 深度设计与文档化

本 skill 将持续检验用户的计划、决策或想法，直到形成共同理解；同时在领域术语和重要决策明确时，及时把它们记录到项目文档中。

## 深度设计

持续追问用户，直到你们达成共同理解。把讨论映射成一棵**设计树**：每个决策都展开出依赖它的后续决策。

按**轮次**推进。**前沿问题**（frontier）是所有前置条件已经确定的决策：也就是当前可以提问、而不需要猜测尚未得到的答案的问题。

每一轮都使用 **ask_user_question** tool来提问问题和提供推荐回答

每轮从当前前沿问题中选择最多 6 个互不依赖且影响最大的决策，依次按阻塞程度、风险和信息增益排序，未进入本轮的问题保留到后续轮次。

用户回答后重新计算前沿，已失效的问题直接移除。然后等待用户回答，再进入下一轮。

用户每轮的回答都会重塑设计树：已确定的决策会推动前沿向外扩展，并解除依赖这些决策的问题。重新计算前沿，再提出下一轮问题。如果一个问题依赖于本轮中仍未解决的另一个问题，就把它放到后续轮次，而不是在当前轮次猜测。

**事实由你负责查找，不要让用户提供本可从环境中获取的事实。**如果某个前沿问题需要文件系统、工具或其他环境事实，就调度子代理或使用可用工具查明；不要把这类事实问题抛给用户，也不要因此阻塞其他不依赖该事实的问题。**决策由用户负责**：把决策问题交给用户，并等待其回答。

当所有前沿问题都已清空、每个分支都被检查过且没有未声明的假设时，本次会话才算完成。在用户确认你们已经达成共同理解之前，不要开始执行基于该设计的实际改动。

用户跳过且存在安全默认值：采用范围最小、风险最低、可逆的默认值，并标记为“暂定假设”；不存在安全默认值：列为未决事项，不要立即反复追问。

用户取消提问：结束当前设计轮次，不宣称设计完成。

## 文档化

在设计过程中主动建立并不断校准项目的领域模型。这是一项主动工作：质疑术语、设计能暴露边界的具体场景，并在术语或决策刚刚明确时立即写入术语表和决策记录。仅仅读取现有 `CONTEXT.md` 获取词汇不算执行领域建模；本节适用于正在改变或明确领域模型的场景。

### 文件结构

大多数仓库只有一个领域上下文：

```text
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，则仓库包含多个上下文。该映射文件会指出每个上下文的位置及其关系：

```text
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文级决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

按需创建文件：只有确实需要写入时才创建。如果不存在 `CONTEXT.md`，在第一个术语确定时才创建；如果不存在 `docs/adr/`，在第一个 ADR 确实需要记录时才创建。

### 单上下文与多上下文仓库

**单上下文（最常见）：**在仓库根目录放一个 `CONTEXT.md`。

**多上下文：**仓库根目录的 `CONTEXT-MAP.md` 列出各个上下文、它们的位置以及相互关系：

```md
# 上下文映射

## 上下文

- [订单](./src/ordering/CONTEXT.md)：接收并跟踪客户订单
- [计费](./src/billing/CONTEXT.md)：生成发票并处理付款
- [履约](./src/fulfillment/CONTEXT.md)：管理仓库拣货和发货

## 关系

- **订单 → 履约**：订单上下文发布 `OrderPlaced` 事件；履约上下文消费该事件并开始拣货
- **履约 → 计费**：履约上下文发布 `ShipmentDispatched` 事件；计费上下文消费该事件并生成发票
- **订单 ↔ 计费**：共享 `CustomerId` 和 `Money` 类型
```

根据以下规则推断仓库属于哪种结构：

- 如果存在 `CONTEXT-MAP.md`，读取它以找到各个上下文；
- 如果只有根目录的 `CONTEXT.md`，则视为单上下文；
- 如果两者都不存在，在第一个术语确定、确实需要记录时，按需创建根目录的 `CONTEXT.md`。

存在多个上下文时，推断当前主题属于哪个上下文。如果无法判断，就向用户提问。

### 会话中的领域建模行为

#### 对照术语表进行质疑

如果用户使用的术语与现有 `CONTEXT.md` 中的语言冲突，立即指出。例如：

> 术语表把“取消”定义为 X，但你现在似乎指的是 Y。这里应当采用哪一种含义？

#### 明确模糊语言

当用户使用含糊或多义的词语时，提出一个精确的规范术语。例如：

> 你说的是“账户”：这里指的是 Customer（客户）还是 User（用户）？它们是两个不同的概念。

#### 讨论具体场景

讨论领域关系时，用具体场景进行压力测试。主动设计能够暴露边界条件的例子，迫使概念之间的边界变得明确。

#### 与代码交叉核对

当用户描述系统行为时，检查代码是否一致。如果发现矛盾，明确指出。例如：

> 代码会取消整个 Order（订单），但你刚才说可以部分取消。哪一种才是正确的领域规则？

#### 就地更新 `CONTEXT.md`

术语一旦明确，就立即更新 `CONTEXT.md`，不要等会话结束后批量补写。使用下方“`CONTEXT.md` 格式”中的格式。

`CONTEXT.md` 必须完全不包含实现细节。不要把它当作规格说明、草稿或实现决策仓库；它只是术语表。

## `CONTEXT.md` 格式

### 结构

```md
# {上下文名称}

{用一到两句话说明这个上下文是什么，以及它为什么存在。}

## 语言

**订单**：
{用一到两句话描述这个术语。}
_避免使用_：购买、交易

**发票**：
交付完成后发送给客户的付款请求。
_避免使用_：账单、付款请求

**客户**：
下达订单的个人或组织。
_避免使用_：用户、买家、账户
```

### 规则

- **要有明确立场。**同一个概念有多个词时，选出最合适的规范术语，并把其他词列在 `_避免使用_` 下。
- **定义要简洁。**最多一到两句话。定义它“是什么”，而不是定义它“做什么”。
- **只记录项目领域特有的术语。**通用编程概念（例如超时、错误类型、工具模式）即使在项目中大量使用，也不属于这里。添加术语前先问：这是该领域特有的概念，还是通用编程概念？只有前者才应加入。
- **自然形成主题簇时使用小标题分组。**如果所有术语都属于同一块紧密领域，则使用扁平列表即可。

## ADR 格式

ADR 存放在 `docs/adr/` 中，并使用连续编号：`0001-slug.md`、`0002-slug.md` 等。

仅在确实需要记录第一个 ADR 时才按需创建 `docs/adr/` 目录。

### 模板

```md
# {简短的决策标题}

{用一到三句话说明背景、作出的决定以及作出该决定的原因。}
```

仅此即可。ADR 可以只有一个段落。记录的价值在于说明“作出了什么决定”以及“为什么”，而不是填满固定章节。

### 可选章节

只有确实有价值时才加入；大多数 ADR 不需要这些章节：

- **状态**前置元数据（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：适合会被重新审视的决定；
- **考虑过的选项**：只有被否决的替代方案值得保留时才加入；
- **后果**：只有需要特别说明不明显的下游影响时才加入。

### 编号

扫描 `docs/adr/`，找到现有最高编号，然后加一。

### 何时提供 ADR

以下三个条件必须全部满足：

1. **难以逆转**：以后改变决定的成本很高；
2. **没有背景会令人意外**：未来读者看到代码时会疑惑“为什么偏偏这样做”；
3. **确实存在权衡**：有真实的替代方案，而当前选择是基于具体理由作出的。

如果一个决定很容易逆转，就跳过它——因为很可能真的会改回去。如果它并不令人意外，就不会有人追问原因。如果不存在真实替代方案，也就没有需要记录的取舍，只是做了显而易见的事情。

### 哪些内容值得记录

- **架构形态。**例如“采用 monorepo”“写模型使用事件溯源，读模型投影到 Postgres”。
- **上下文之间的集成模式。**例如“订单和计费通过领域事件通信，而不是同步 HTTP”。
- **会造成锁定的技术选择。**数据库、消息总线、身份认证提供商、部署目标等；不是每个库都需要记录，只记录更换成本可能达到一个季度的选择。
- **边界与范围决策。**例如“客户数据由客户上下文负责，其他上下文只能通过 ID 引用”。明确哪些事情不做，与明确哪些事情要做同样有价值。
- **有意偏离显而易见路径的决定。**例如“由于 X，使用手写 SQL 而不是 ORM”。如果合理读者会默认采用相反方案，就应记录，避免后续工程师把有意为之的设计“修正”掉。
- **代码中看不出来的约束。**例如“由于合规要求不能使用 AWS”“由于合作方 API 合约，响应时间必须低于 200ms”。
- **被否决的替代方案，且否决理由不明显。**如果考虑过 GraphQL、最终因微妙原因选择 REST，就记录下来；否则六个月后可能又有人重新提议 GraphQL。

## 执行结束条件

在以下条件全部满足前，不要宣称设计或领域建模已经完成：

- 设计树的所有前沿问题都已处理；
- 用户确认双方已经达成共同理解；
- 已明确的领域术语已经即时写入正确的 `CONTEXT.md`；
- 满足三个条件的架构或领域决策已经记录为 ADR；
- 没有把实现细节混入 `CONTEXT.md`，也没有留下未声明的关键假设。
