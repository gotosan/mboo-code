# 深度设计与文档化

通过事实调查、设计树和分轮决策形成可执行的共同理解，并把适合长期保留的术语和决策写入项目既有文档。

## 执行边界

如果当前请求只是简单事实查询、可直接从仓库或工具确认的问题，或者范围已经明确的短任务，直接完成请求，不要为了执行本 skill 人为建立设计树或调用 `ask_user_question`。

用户要求只读、只给方案或不修改文件时，只调查和输出设计结果，不写入术语表、ADR、代码或配置。激活本 skill 本身不代表用户授权修改文件。

## 事实调查

开始提问前，先读取适用的项目规则、相关设计文档和代码，确认已有约束、术语与决策。使用当前运行时提供的文件、搜索、命令或网络工具查明环境中可获得的事实；工具无法验证的内容要明确标记为事实缺口。

事实由你负责查找，不要把本可从环境获取的问题抛给用户。需要业务取舍、范围选择或风险接受的决策由用户负责。

## 设计树

把讨论映射成一棵设计树：每个决策展开出依赖它的后续决策。**前沿问题**是前置条件已经确定、当前可以回答而不需要猜测其他未决答案的决策。

只把会实质影响范围、边界、接口、数据、验收、不可逆成本或风险的问题纳入设计树。普通实现偏好优先采用项目惯例或可逆默认值，不展开为低价值分支。

用户回答后更新设计树：确认或暂定的决策解锁后续问题，已失效的问题直接移除，依赖尚未满足的问题留到后续轮次。

## 分轮提问

每个需要用户决策的轮次使用一次 `ask_user_question`，不得并发发起多个提问调用。

每轮从当前前沿中选择 1～6 个互不依赖且影响最大的决策，依次按阻塞程度、风险和信息增益排序；未进入本轮的问题保留到后续轮次。每个问题页必须：

- 只表达一个独立决策；
- 提供 1～3 个互斥且处于同一层级的选项；
- 恰好设置一个推荐项，并把推荐项放在第一位；
- 在选项描述中说明主要影响和推荐理由；
- 使用纯文本，问题和选项文本分别不超过 200 个字符，选项描述不超过 500 个字符。

推荐答案只是建议，不能在用户选择前记为已确认决策。

## 回答与异常

- **正常回答**：按用户选择更新设计树，再重新计算前沿。
- **跳过且有安全默认值**：采用范围最小、风险最低且可逆的默认值，并标记为“暂定假设”。
- **跳过且没有安全默认值**：列为未决事项，不立即反复追问。
- **取消**：取消会终止整个当前执行 turn，不产生可供同一 turn 继续处理的正常答案；不要宣称设计完成，也不要计划在取消后继续写文档。
- **`ASK_EXPIRED`**：把本组问题保留为未决事项，不把过期当作跳过或默认答案，也不立即原样重新提问。
- **`ASK_CONCURRENT_UNSUPPORTED`**：不把失败调用解释为用户回答，不重复发起并行提问；等待已有交互结束或在后续 turn 恢复。

暂定假设和未决事项都不能写成已确认术语或已接受的 ADR 决策。

## 场景检验与收敛

用正常流程、边界条件、失败流程和兼容场景检验已确认设计。场景暴露新的高影响决策时，将其加入设计树；只暴露普通实现细节时，按项目惯例处理。

当所有高影响决策都已确认、采用明确的暂定假设或被显式延期，并且没有未声明的关键假设时，停止追问。不要为了覆盖所有理论分支而无限扩展设计树。

最终设计结果至少说明：

- 目标与非目标；
- 已确认决策及理由；
- 关键边界、流程、接口或数据约束；
- 暂定假设及验证方式；
- 未决或延期事项；
- 主要风险与验收标准；
- 候选术语、ADR 候选和拟修改文档；
- 本轮明确没有执行的操作。

如果用户同时要求后续实现，在设计形成共同理解前不要开始代码或配置改动。

## 文档化

只有当前讨论确实改变或明确了项目术语、领域边界或值得长期保留的决策时，才执行文档化；不要为每次设计讨论强行创建术语或 ADR。

第一次需要判断、建议或写入术语表、上下文映射或 ADR 前，使用 `read_skill_resource` 读取 `references/文档化约定.md`，并遵循其中的发现顺序、现有格式优先原则和 fallback 规则。

实际创建或修改文档还必须满足：

- 当前用户明确要求更新文档或随后明确授权写入；
- 写入范围没有被只读、只给方案或不修改文件等要求排除；
- 使用正常文件工具并遵守工作区、权限和项目规则。

写入前先发现仓库已有文档入口和格式。`CONTEXT.md` 是指针、链接或迁移说明时，继续读取并维护它指向的唯一目标文件，不覆盖入口，也不创建重复术语表。术语表和 ADR 的现有路径、语言、标题层级、别名标记、文件名和章节风格优先于本 skill 的默认模板。

只把用户已确认的术语与决策写入权威文档。没有写入授权、写入失败或工具不可用时，输出建议修改位置和拟写内容，不得声称已经落盘。

## 完成条件

在以下条件全部满足前，不要宣称设计和文档化已经完成：

- 所有高影响决策已确认、明确暂定或显式延期；
- 用户确认双方对最终设计形成共同理解；
- 暂定假设、未决事项和验证方式已明确列出；
- 满足条件且获准写入的术语与 ADR 已写入正确的既有文档；
- 没有获准写入的内容已作为建议列出，而不是描述为已完成；
- 没有把候选建议写成用户决策，也没有留下未声明的关键假设。
